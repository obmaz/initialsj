# 성능 분석과 검증

현재 성능 판단의 근거와 남은 개선 과제를 관리합니다. 적용한 동작의 정본은 [ARCHITECTURE.md](ARCHITECTURE.md)이며 측정 스크립트·원자료·화면은 Git에서 제외한 `build/reports/`에 둡니다.

## TRACK02 프레임 저하

### 증상과 판단

Android APK1.0.37을 갤럭시 폴드8의 펼친 화면·고화질로 플레이할 때 약20fps까지 떨어졌다는 제보입니다. 한 바퀴 뒤 관중석이 보이기 시작하는 구간과 일부 다른 구간에서 발생했습니다. 실제 기기에 연결한 CPU·GPU 계측은 아직 없습니다.

원인은 CPU 계산과 렌더링 부하를 함께 고려합니다. TRACK02는 상대15대의 차체 물리·곡률·앞차 판단 비용이 크며, 고화질은 큰 화면의 픽셀 수와 그림자 비용도 컸습니다. 트랙 간 드로 콜·삼각형 수의 비율만으로 GPU 병목을 제외하지 않습니다. 파일 미리 읽기와 첫 렌더 준비는 이미 수행하고 있어, 모든 에셋을 더 미리 읽는 것만으로 반복되는 저하를 해결할 근거는 부족합니다.

### 물리 틱과 시간 배율

`Engine.time_scale = 1.2`는 물리 틱의 시뮬레이션 시간을 16.67ms에서20ms로 늘립니다. 초당 실행 횟수를 60회에서72회로 늘리지는 않습니다. Godot4.7.2에서 배율1.0·1.2·2.0을 각각 약2.5초간 실행했을 때 모두 약60회/초였습니다. 프레임 지연 시 여러 물리 틱이 한 렌더 프레임에 실행될 수 있지만, 실제 폴드에서20fps가 된 원인이 이것이라고 확정하지 않습니다.

## 변경 전후 비교

기준 소스는 `c38d913`입니다. CPU 비교는 같은 게임의 변경 전 상대 차량 제어기·직접 곡률 계산과 변경 후 제어기·곡률 표 조회를 번갈아 사용했습니다. 플레이어와 차량 수, 실제 차체 물리는 유지했습니다. 원자료는 `build/reports/track2-optimization/`에 있습니다.

### CPU

헤드리스 Godot4.7.2에서 실제 `race._physics_process()`를 측정했습니다. TRACK02의80m·4400m·5600m에서 실제 차체 입력으로 각각150틱을 진행하고 최초12틱을 제외했습니다. 조건별1,242표본이며 세 번 반복하고 실행 순서를 바꿨습니다. 전체 시간은 구간별 측정값을 합산하지 않고 함수 진입·복귀에서 직접 잰 값입니다.

| 16대 배치 | 중앙값 전→후 | p95 전→후 | 중앙값 감소 |
| --- | --- | --- | --- |
| 가까이 밀집 | 8.38→6.88ms | 11.14→9.01ms | 약18% |
| 코스에 분산 | 5.72→3.57ms | 7.38→4.48ms | 약38% |

이는 자동 주행 한 바퀴 전체의 평균이나 Android에서 측정한 시간이 아닙니다. 곡률 표는 5개 트랙 모두 원래 계산과 비교하고 음수 거리·랩 경계를 검사합니다. 표의 float 자료는 코스별 약22~46KB이며 매 바퀴 추가되지 않습니다. 먼 차량의 계획 재사용 중에도 이동·니트로·노면 타이머는 매 틱 진행하며 근접 계산 복귀와 순간이동 초기화를 검사합니다. 별도의16대 실제 차체 주행에서 플레이어가 순서 있는 게이트를 통과해 한 바퀴를 완료했습니다.

### 렌더링

네이티브 GL Compatibility·Mesa llvmpipe 소프트웨어 렌더러에서1280×720으로 같은 시점을 변경 전·후·후·전 순서로 비교했습니다. 재질 준비 뒤 조건마다8프레임을 안정화하고18프레임을 측정했습니다. 변경 후에는 Android 고화질 정책과 3샘플 속도 블러를 적용했습니다. 이 해상도에서는 3D 축소가 없어 그림자·블러 변경을 비교합니다.

| 위치 | 그림자 삼각형 전→후 | 렌더 대기 포함 프레임 시간의 상대 감소 |
| --- | --- | --- |
| 80m | 244,868→124,250 | 약18% |
| 4400m | 249,668→127,136 | 약14% |
| 5600m | 244,248→123,594 | 약19% |

소프트웨어 렌더러의 시간은 폴드의 GPU 시간이나 FPS로 환산하지 않습니다. 모바일 고화질의1920×1080 상한은 화면 비율을 유지하며3D에만 적용하고 UI 해상도는 보존합니다. `canvas_items`의 창 배율을 중복 반영하던 계산도 실제 픽셀 영역 기준으로 수정해 상한보다 과도하게 축소하지 않습니다. 작은 화면은 확대·추가 축소하지 않습니다. 고화질을 임의로 자동·성능 모드로 바꾸지는 않습니다.

## 투어 곡률 캐시 검토

투어는 레이싱 상대를 비활성화하며 일반 교통 차량의 [tour_traffic.gd](../scripts/race/tour_traffic.gd)는 곡률 대신 실제 위치 투영·앞쪽 목표점·차체 물리를 사용합니다. 상시 곡률 호출은 플레이어의 드리프트 보상과 코너 예고에 각각 한 번씩입니다.

헤드리스 Godot4.7.2에서 하와이·정글·도시·피라미드·서울·설원의 중립 진입을 측정했습니다. 지역별10%·50%·90% 위치에서100틱을 진행하고 최초10틱을 제외해 총1,620표본을 모았습니다. 모든 표본에서 곡률은 틱당2회였고 합계 중앙값은 0.011ms, 지역별 평균은 0.012~0.016ms였습니다. 계측한 주행 콜백 시간의 약1~1.6%이며 독립 교통 차량 콜백·렌더링을 포함한 전체 프레임 비중은 아닙니다. 원자료는 `build/reports/track2-optimization/tour-curvature.json`에 둡니다.

투어에도 구간별 캐시를 도입할 수 있지만, 이번 측정에서는 상시 곡률을 전부 없애더라도 절감 상한이 작습니다. 지역 전환 순간의 끊김까지 해결한다고 해석하지 않습니다. 구현 시 구간 준비에 표 생성을 나누고, 이전 구간·두 갈림길·재선택에 걸친 질의 거리 앞뒤14m 처리를 보존해야 합니다. [곡률 캐시 계약](MODEL_PIPELINE.md#곡률-캐시-계약)을 따르며 곡률 캐시는 투어 실행 경로에 추가하지 않았습니다.

## 남은 확인과 개선 후보

1. 실제 폴드에서 같은 구간을 여러 바퀴 주행하며 CPU·GPU 시간, 발열과 프레임 간격을 함께 확인합니다. 펼침·고화질 조건을 유지하고 출발 직후와 관중석 재진입을 구분합니다.
2. 가까운 상대 차량의 `world_car.gd` 내부 비용을 더 나눠 측정합니다. 접지 레이·충돌 스윕만이 차체 물리 비용의 대부분이라고 판단하지 않습니다. 주행감·접촉 결과가 같은 개선부터 선택합니다.
3. 넓은 가드레일·커브·울타리 배치의 공간 분할을 검토합니다. 코스 전체를 덮는 단일 Mesh·MultiMesh는 일부만 보이더라도 큰 범위를 처리할 수 있습니다. 분할 시 드로 콜 증가와 가시성 감소를 함께 비교하고 [모델 원본 보호 규칙](MODEL_PIPELINE.md)을 따릅니다.
4. 투어 곡률 캐시는 현재 측정에서 우선순위가 낮습니다. 다른 진입 변형·끝 경계·실제 기기에서 필요성이 확인되면 열린 도로의 끝 처리·갈림길과 구간 수명을 보존해 도입합니다. 이번 닫힌 코스용 캐시를 그대로 적용하지 않습니다.

차량 수 감소나 근접 차량의 물리 주기 축소는 아직 적용하지 않았습니다. 프레임 수에 따라 순위·추월·접촉 규칙이 달라지는 자동 조정도 추가하지 않았습니다.

투어43개 진입 준비는 코스의 `assembly/part_*.tscn`을 순차 연결합니다. 큰 `PackedScene.instantiate()` 한 번에 의존하지 않으며 GLB 메시 조회는 `SceneState`의 저장된 `mesh` 속성과 공용 래퍼를 읽습니다. 노드를 생성했다가 바로 해제하는 조회는 하지 않습니다. 교통 차체는 개별 준비 단계에서 연결합니다. 재질 미리 렌더도 메시 ID를 구분하므로 같은 재질의 다른 메시 업로드를 누락하지 않습니다. 조립 계약은 [모델 파이프라인](MODEL_PIPELINE.md#큰-조립-씬의-분할-준비)을 따릅니다. 실제 모바일 GPU·발열 조건의 FPS 보장은 별도 실기기 측정이 필요합니다.


## 투어 전환·주행 및 야간 강수

지역 전환뿐 아니라 다음 갈림길을 준비하는 동안에도 메인 스레드의 씬 생성·메시 연결 작업이 실행됩니다. 서울 외의 조립 씬은 수백 노드를 한꺼번에 생성했으며, 파일 미리 읽기 이후에도 같은 프레임에 GLB 속성 순회와 상태 복원이 몰릴 수 있었습니다. 기본 지역 프로필을 저장 씬의 인자 없는 생성자에서 중복 초기화하는 작업도 있었습니다.

현재43개 투어 진입은 24노드 이하의 저장 씬으로 나누고, 큰 GLB의 저장 속성 순회도 24노드·0.5ms씩 이어 갑니다. 메시·월드 메타정보는 4노드, 저장 상태는 1노드 단위로 연결합니다. 저FPS의 보충 물리 틱이 같은 렌더 프레임에서 준비 예산을 중복 소비하지 않도록 `maintain()`도 프레임당 한 번만 실행합니다. 주행 중 GPU 미리 렌더는 128×64·프레임당1작업으로 제한하며 로딩 화면 뒤의 준비량은 유지합니다. 작업 중 취소 시 조립 루트·조회 중 SceneState·파일 참조를 함께 비웁니다. 모델 원본·배치·공통 형상은 유지합니다. 사용하지 않는 진입 연결부의 배포 파일만 정리하고 원본은 `source_only`로 계속 보호합니다.

날씨는 이미 계측한 플레이어 거리를 사용하고 교통 차량은 생성 시 확정한 거리부터 국소 투영합니다. 매 프레임·물리 틱마다 도로 전체를 최근접 검색하지 않습니다. 실제 차체 이동·충돌 주기는 유지하며 굽은 구간·높낮이·양 차선에서 국소 거리 복원을 검사합니다. 숨겨진 지역은 지역 광원·놀이기구 갱신을 쉬고, 광원 거리 판정은 0.15초마다 상태가 바뀔 때만 전달합니다.

모바일 야간 비는 고화질 선택을 유지하면서3D 상한1600×900, 실제 거리 광원 최대2개, 비 최대160개를 사용합니다. UI는 원래 해상도이며 작은 화면은 추가 축소하지 않습니다. 비구름 아래 달 그림자 맵은 생략하고 노면 접촉 음영·전조등·광고 발광·젖은 반사를 유지합니다. 맑은 날과 다른 시간대에는 원래 예산을 복구합니다. 모바일 고화질1920×1080 상한과 비교하면 큰 화면의 픽셀 상한은 약31% 작습니다.

Godot4.7.2의 네이티브 GL Compatibility·Mesa llvmpipe에서 TRACK02의80m·4400m·5600m를 이전 정책→새 정책→새 정책→이전 정책 순으로 비교했습니다.1280×720의 이 비교에는 3D 해상도 축소가 없으며, 각 조건의8프레임 안정화 후12프레임을 관측했습니다. 조건당 두 번 측정에서 프레임 시간 중앙값의 평균은 약15~19% 줄었습니다. 실제 드로 콜은 286→223,348→264,298→245였고 달 그림자 삼각형 약12~13만 개가 제거됐습니다. 이는 Android GPU·폴드의 FPS 측정이 아니며 실기기에서의 발열·지역 전환·지속 주행 확인은 남아 있습니다.

분기 전후에 추가됐던120m 연결부는 원래 중심선·기믹 거리로 복구했습니다. 중앙 틈의 실제 충돌벽과 즉시 안전 복구는 유지하며 원래 코스와 다른 기록·고스트가 섞이지 않게 `tour_routes_v3`를 사용합니다. 측정 원자료와 네이티브 화면은 `build/reports/tour-weather-performance/`에 둡니다.
