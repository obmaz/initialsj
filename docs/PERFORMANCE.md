# 성능 분석과 개선 제안

주행 중 프레임 저하의 원인 분석과 아직 적용하지 않은 개선 제안을 관리합니다. 제안을 적용하면 해당 항목을 지우고 동작 설명은 [ARCHITECTURE.md](ARCHITECTURE.md)로 옮깁니다. 측정 스크립트와 원자료는 커밋하지 않고 `build/reports/`에 둡니다.

## TRACK02 프레임 저하

### 증상

SUNCOAST SPEEDWAY(TRACK02)에서 주행 중 간헐적으로 약 20fps까지 떨어집니다. 다른 트랙에서는 아직 확인하지 않았습니다.

### 결론

그래픽이 아니라 CPU에서 실행되는 물리 틱(차체 물리와 상대 차량 판단)이 병목일 가능성이 큽니다. 실제 기기에서는 측정하지 않았으며, 아래 수치는 모두 헤드리스 데스크톱(커밋 `952e111`) 기준입니다. 기기별 절대값은 다르므로 트랙 간 비율과 항목별 비중으로 읽습니다.

### 측정

| 항목 | TRACK02 | TRACK01 |
| --- | --- | --- |
| 상대 차량 | 15대 | 7대 |
| 물리 틱 1회 평균(자동 주행 한 바퀴) | 6.7ms | 2.4ms |
| 물리 틱 1회 최악 | 18ms | 11ms |
| 드로 콜(가상 디스플레이 렌더) | 440~620 | 320~370 |
| 프레임당 삼각형(그림자 패스 포함) | 33만~50만 | 40만~42만 |

그리기 부하는 드로 콜이 약 50% 많은 정도이고 물리 틱은 약 3배입니다.

### 20fps까지 떨어지는 과정

1. 물리 틱은 초당 72번 실행됩니다. 기본 60번에 [race.gd](../scripts/race/race.gd)의 `GAME_PACE` 1.2가 `Engine.time_scale`로 곱해집니다.
2. 틱이 7ms이면 측정 환경에서도 코어 하나의 절반을 씁니다. 기기가 2배 느려 틱이 14ms가 되면 72번에 1초가 모두 들어갑니다.
3. 프레임 안에 틱을 끝내지 못하면 엔진이 한 프레임에 여러 틱을 몰아 실행합니다. 프레임당 3~4틱이면 약 20fps가 됩니다.
4. 롤링 스타트 직후와 오벌 특성상 차량이 뭉쳐 가까운 차가 늘면 틱이 15~18ms까지 올라갑니다. 저하가 간헐적인 이유입니다.
5. [render_budget.gd](../scripts/rendering/render_budget.gd)는 fps가 떨어지면 그림자와 해상도만 낮춥니다. 병목이 CPU이면 회복되지 않습니다.

### 틱 안의 비용

[world_race.gd](../scripts/race/world_race.gd)에 임시 계측을 넣어 TRACK02에서 4,200틱을 평균했습니다.

| 항목 | 틱당 시간 | 내용 |
| --- | --- | --- |
| 가까운 상대 차량의 차체 물리 | 3.5ms | 틱당 약 6대, 대당 0.6ms |
| 상대 차량의 속도·조향 판단 | 2.25ms | 15대 모두 매 틱, 대당 0.17ms(TRACK01은 0.07ms) |
| 플레이어 차체 물리 | 0.8ms | 1대 |
| 먼 차량 이동 처리 | 0.67ms | 틱당 약 7대 |
| 진행 계측과 기타 | 약 1.1ms | |

- **먼 차량도 판단 계산을 생략하지 않습니다.** `update_rivals()`는 150m 밖의 차량에 대해 차체 물리만 건너뛰고(`carry_rival()`), 앞쪽 다섯 지점의 `curvature()`와 주변 차량 탐색은 모든 차량에 대해 매 틱 실행합니다.
- **곡률은 코스에 고정된 값인데 매번 다시 구합니다.** `curvature()` 한 번은 `point()` 네 번이고 `point()`는 곡선을 세 번 표본화합니다. 차량 한 대가 틱마다 `point()`를 약 24번 호출합니다. TRACK02는 `point()` 안의 폭·뱅크 계산이 더 무거워 대당 비용이 TRACK01의 약 2.5배입니다.
- **차체 물리 한 번이 0.6ms로 무겁습니다.** [world_car.gd](../scripts/physics/world_car.gd)의 접지 레이 5개와 충돌 스윕은 합쳐 0.05~0.1ms 수준입니다. 나머지 비용의 출처는 아직 나누어 재지 않았습니다.

### 원인이 아닌 것

- 충돌 메시 밀도는 트랙별로 비슷합니다. 차 한 대의 스윕 비용은 모든 트랙에서 7~38µs입니다.
- 상대 차량은 대당 3번, 플레이어 차량은 8번에 그려집니다.
- TRACK02 장면 전체는 약 30만 삼각형, 드로 항목 약 260개입니다.

## 개선 제안

아직 적용하지 않았습니다. 예상 효과가 큰 순서입니다.

| 순서 | 제안 | 대상 | 기대 효과 | 주의점 |
| --- | --- | --- | --- | --- |
| 1 | 코스 곡률을 시작할 때 거리별 표로 만들고 조회만 한다 | `road_section.gd`의 `curvature()`, `world_race.gd` | 판단 비용 2.25ms의 대부분 | 닫힌 코스에만 적용한다. 투어는 분기 뒤 구간이 바뀌므로 구간별 표가 필요하다 |
| 2 | 먼 차량은 판단 계산도 여러 틱에 한 번만 한다 | `update_rivals()`, `carry_rival()` | 먼 차량 7대분의 판단과 이동 비용 | 플레이어 근처로 돌아올 때 속도·차선이 튀지 않는지 확인한다 |
| 3 | 가까운 차량의 물리 주기를 거리와 화면 노출에 따라 더 나눈다 | `rival_stride()` | 차체 물리 3.5ms의 일부 | 접촉 중이거나 공중인 차량은 지금처럼 매 틱 계산한다 |
| 4 | fps가 떨어지면 그래픽과 함께 상대 차량 계산 주기도 낮춘다 | `render_budget.gd`, `world_race.gd` | CPU 병목에서도 자동 회복 | 순위·추월 판정이 주기에 따라 달라지지 않게 한다 |
| 5 | 차체 물리 0.6ms의 내부 비용을 나누어 잰 뒤 줄인다 | `world_car.gd`의 `advance()` | 차량 수에 비례하는 전체 비용 | 주행감 검사가 있으므로 결과가 같은 최적화만 한다 |
| 6 | 플레이어 뒤쪽 먼 차량은 대수를 줄이거나 표시만 한다 | `race.gd`의 `competitor_count()` | 차량 수 자체 | 게임 규칙 변경이므로 별도 결정이 필요하다 |

`GAME_PACE`를 낮추면 틱 수는 줄지만 체감 속도가 바뀌므로 성능 대책으로 쓰지 않습니다.

## 확인이 필요한 것

- 실제 휴대폰과 WebGL에서의 틱 시간과 fps. 증상이 Android APK인지 웹인지, 출발 직후인지 주행 내내인지에 따라 우선순위가 달라집니다.
- 다른 트랙과 투어의 같은 측정. 차량 수가 적어 틱은 가볍지만 투어는 교통 차량과 구간 생성 비용이 따로 있습니다.
- 제안을 적용한 뒤의 재측정. 같은 조건(자동 주행 한 바퀴, 틱당 평균과 최악)으로 비교합니다.
